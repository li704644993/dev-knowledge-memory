# Development Memory

Read [settings.json](settings.json) beside this skill to determine work roots, the development knowledge directory, MCP server, and memory project. It is generated by this repository's installer; if missing, report incomplete installation. Do not guess paths or choose a different knowledge project.

## Scope

Apply only to repositories under the configured work roots, their Git worktrees, and tasks explicitly targeting those repositories. For a worktree outside a root, confirm its Git common directory belongs to a configured repository. Do not activate merely because an unrelated task uses the same keyword.

Only the configured development directory is an Obsidian knowledge source. Do not search the entire vault or follow links into Research, daily notes, or another vault folder unless the user explicitly expands the scope. Repository source/configuration/docs and explicitly requested external documentation can be read as needed; any resulting development knowledge stays in the development directory. General external research keeps its separate workflow.

Discover the configured MCP tools if necessary. Use the configured project on every call. If the service is unavailable, report it rather than silently switching to whole-vault search or another provider. A retrieval failure is not a zero-result search. Unaffected read-only investigation can continue; a knowledge-dependent mutation must not proceed on a guess.

## Before Work

1. Extract business terms, versions, technical identifiers, and aliases from the task. Use `search_notes` with `search_type="text"` for exact identifiers and `search_type="hybrid"` for concepts. Do not limit durable topic searches to recent days. Use short, focused queries rather than an entire requirement as an exact match.
2. Read relevant results with `read_note`, `include_frontmatter=true`. Scores and snippets are not sufficient evidence. Follow relevant links only within the development knowledge scope. Do not preload the library.
3. Distinguish vocabulary, the current mechanism, and historical changes. Check the note's status, verified scope, sources, and code revision. Partial or unverified notes are leads, not complete specifications.
4. Verify the live code necessary for this task: entity ID semantics, ownership, business entry points, and required side effects. Do not re-explore unrelated subsystems when the note already supplies adequate pointers. A model/table mapping alone is not a write procedure.
5. Briefly name the useful notes and material discrepancies. With zero relevant notes, acknowledge the gap and perform targeted source investigation. Capture confirmed findings at completion.

## Automatic Completion Capture

The standing configuration authorizes development-knowledge capture in the configured directory. Do not require a separate "remember this" prompt or the server's generic first-note onboarding confirmation. This does not authorize unrelated actions.

At completion of development or a confirmed business-code investigation, before the final reply:

- Search for existing knowledge before writing. Update the canonical topic when its mechanism changes; preserve unrelated content and avoid a new copy for each requirement.
- Use `concepts/` for vocabulary, aliases, entity/model mappings and ID semantics; `topics/` for current mechanisms and source entry points; `changes/` for dated decisions, root causes and rejected approaches with material reuse value.
- Do not generate a note for every conversational turn or trivial wording change. If no useful new knowledge emerged, no write is needed.
- For an existing note, read first and use `edit_note` for the affected section, or an intentional merged replacement. For a new note, use `write_note` with `overwrite=false`. Always pass the configured project and preserve the returned permalink.
- Use the user's or project's documentation language. Preserve technical symbols exactly. Record aliases in both metadata and searchable text, repository identities, source paths/symbols, the checked revision, verification scope and actual deployment state. Mark local uncommitted code explicitly.
- Use accurate statuses: `planned`, `implemented-unverified`, `verified`, `imported-partially-verified`, or `superseded`. Date the actual check, not an assumed deployment. Do not invent the original author's rationale.
- Set `publish: false`; do not automatically publish notes, migrate research notes, or include credentials/full tool logs. Consult [note-format.md](references/note-format.md) when drafting a substantial note or importing existing documentation.
- Confirm the saved note with `read_note` and, if needed, its materialized file. Pending or failed writes are not completed saves. Report errors and the actual paths updated in the final reply, or state that no new reusable knowledge warranted capture.

Task interruption can prevent completion capture. There is no background agent that runs after the user stops the task. A later continuation should read the current state before resuming capture.

## Business-Write Boundary

Do not execute direct database writes unless explicitly requested by the user. Even then, establish the supported business path and any required side effects rather than translating a retrieved table mapping into an arbitrary SQL update. Note capture does not authorize tests, new infrastructure, extra security mechanisms, recovery paths, or other functionality beyond the current task and repository instructions.
